# PINGOO expansion audit and implementation plan

Audit date: 2026-10-11
Repository: https://github.com/youssefaitlh-collab/pingoout
Branch: codex/pingoo-expansion

## Repository audit

- Framework: Next.js App Router, React 19, TypeScript 5.9, Tailwind CSS v4.
- Deployment assumptions: Netlify build plugin and Netlify environment variables; the repo also contains Vercel-aware canonical URL fallback.
- Catalog source of truth: `lib/games.ts`, importing source-checked records from `lib/verified-games.js`.
- Current published catalog: nine verified records. Demo records remain in `allGames` for legacy routes, are marked noindex, and are excluded from discovery and sitemap.
- Validation: `validateCatalog()` checks stable IDs/slugs, source dates, source URLs, requirements/platform consistency, and provenance for verified claims. Existing test suite is `tests/catalog.test.mjs`.
- Game detail route: `app/games/[slug]/page.tsx`; it already renders game facts, requirements, platforms, sources, breadcrumbs, and VideoGame JSON-LD.
- SEO: `lib/seo.tsx` centralizes metadata, canonical URLs, Open Graph/Twitter metadata, JSON-LD and preview noindex behavior. Sitemap index and pages are generated by `app/sitemap.xml/route.ts` and `app/sitemaps/[id]/route.ts`.
- Navigation: `components/Header.tsx` and `components/MobileMenu.tsx`.
- Existing external integrations: Netlify Forms for contact. No authentication, database, realtime messaging, or payment SDK/dependency is declared in `package.json`.
- Project instructions in `AGENTS.md` prefer Netlify persistence primitives and require existing pages to continue using the shared catalog helpers.

## Risks and decisions

1. Do not insert unsourced records into the published `games` array: that would bypass the existing verified-catalog safeguards.
2. Treat the supplied category names as owner-provided editorial collections, not current sales/trending claims. Any live ranking requires a dated, geography-specific source.
3. Treat platform/experience products such as Roblox distinctly from an individual VideoGame entity when defining structured data.
4. Do not publish fabricated PC requirements, prices, release dates, reviews, ratings, player counts, cross-play claims, or sources. Unknown values remain explicitly unknown.
5. Keep article content and fact provenance in one maintainable typed source of truth and make indexability depend on verification/content readiness.
6. Preserve existing navigation, design tokens, game detail routes, tests, Netlify Forms, and current SEO helpers.
7. Account, wishlist, community, and donation features require real server-side persistence and authorization. They must not be represented as functional until provider credentials, schema/migrations, and runtime behavior are validated.
8. Production verification requires the actual build/test runtime. GitHub file API access alone cannot establish that a production build passed.

## Proposed phases

1. **Audit and safety baseline:** preserve the current catalog contract, inspect current deployment assumptions, and record the feature/configuration boundaries.
2. **Editorial data and research:** add all 56 supplied titles to a structured research register, attach exact authoritative sources where verified, write distinct article content only from supported facts, and emit a machine-readable completion/verification report. Do not label owner-provided rankings as current market facts.
3. **Existing route/SEO integration:** connect publishable articles to the current game-detail architecture; reuse `buildMetadata`, breadcrumbs, structured data helpers, and sitemap utilities. Keep unverified/low-value pages out of the index.
4. **Accounts and wishlists:** select a maintained compatible provider, add server-side authorization, persistent sessions, verified-email and password-reset flows, and ownership-safe wishlist records.
5. **Community:** add game rooms, persistent messages, reports, moderation controls, server validation, rate limiting, safe rendering, and bounded history.
6. **Donations:** verify the provider/account use case, implement sandbox checkout and server-side verified payment state, and document live credentials/webhooks.
7. **QA and release:** run tests, typecheck, lint if configured, production build, route checks, data-isolation tests, and deployment checks. Report every test accurately.

## Required configuration likely to remain external

Exact environment variables and dashboard settings must be finalized after selecting and implementing the provider integrations. Never place OAuth, database service-role, email-provider, or payment secrets in client-side variables. External account eligibility, OAuth redirect URLs, email templates, database permissions, and payment webhooks must be configured in their respective dashboards.
